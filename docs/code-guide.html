The journey of one question

Here's what happens when you type "What does error E-207 mean?" and press Enter. Each step names the code that does it.

  1. You press Enter. ChatInput.jsx calls onSend. App.jsx creates a conversation if this is the first message, then useChatStream.send() starts.
  2. The browser opens a stream. streamChat() in src/api/sse.js sends POST /api/chat and reads the answer piece by piece as it arrives.
  3. The API starts the agent. chat() in app/api/routes_chat.py checks the conversation exists and isn't busy, then runs the agent in a worker thread (_run_turn).
  4. Route (LLM call, cheap model): is this small talk or a question for the documents? It also rewrites follow-ups like "how do I fix it?" into a full question.
  5. Retrieve (no LLM): turn the question into vectors (embeddings), search Qdrant two ways at once (meaning + keywords), merge the two lists, then rerank the 10 candidates and keep the best 5.
  6. Grade (LLM call, cheap model): which of those 5 chunks really help? If none do, rewrite the search query and try again (at most 2 times). If still nothing, say "not found" honestly.
  7. Generate (LLM call, main model, streamed): write the answer from the relevant chunks only, with citations like [1]. Each word is sent to the browser as soon as it's written.
  8. Grounding check (LLM call, cheap model): is every claim supported by the sources? If not, rewrite the answer once. The badge then shows "Verified against sources", "Some claims couldn't be verified" or "Not verified" (the check couldn't run).
  9. Finalize: save the turn in the conversation's memory (Postgres) and send the sources and done events (time and cost).
  10. The UI updates live. Every event becomes a reducer action in useChatStream.js. MessageBubble shows the steps, the streaming text, the clickable citations, the sources and the badge.

Why a stream instead of one normal response? A full answer takes 5–25 seconds. Streaming shows progress and the first words after about a second, so the app feels alive. The Stop button aborts the request, and the server then stops paying for tokens nobody will read (cancel.set() in _run_turn).

Why a worker thread? The agent does slow, blocking work: CPU-heavy embedding and waiting on OpenAI. If that ran on the web server's main loop, every other user would freeze. The thread does the work, and the queue carries events back to the stream as they happen.

Every request and error is logged as JSON (app/logging_setup.py). Settings such as model names, limits and URLs are all read in one place: app/config.py.

What is an embedding?

An embedding turns text into a list of numbers. Texts with similar meaning get similar numbers, so "the thermostat has no power" lands close to "E-114 low power" even though the words differ. We make two kinds for every chunk and every question:

Dense vector: meaning Model BAAI/bge-small-en-v1.5, 384 numbers per text. Good at synonyms and paraphrases. Compared with cosine similarity (how closely two vectors point in the same direction).
Sparse vector: keywords Model Qdrant/bm25. Mostly zeros, with one weight per word that appears. Good at exact terms like E-207 or URLSafeTimedSerializer, which meaning-based search can miss.
# app/retrieval/embeddings.py:47 — both models are loaded ONCE (slow) and reused
self._dense  = TextEmbedding(settings.embed_dense_model, cache_dir=…)        # bge-small
self._sparse = SparseTextEmbedding(settings.embed_sparse_model, cache_dir=…)  # BM25

def embed_query(self, text):                      # embeddings.py:78 — for the user's question
    dense  = next(iter(self._dense.query_embed(text)))
    sparse = next(iter(self._sparse.query_embed(text)))
    return dense.tolist(), SparseVector(sparse.indices.tolist(), sparse.values.tolist())

The models come from FastEmbed and run on your CPU through ONNX: no GPU, no API calls, no cost. They are downloaded once into the model cache.

Hybrid search with RRF: the key idea

# app/retrieval/vectorstore.py:146 — one request, two searches, merged inside Qdrant
kwargs = {
    "prefetch": [
        models.Prefetch(query=dense,        using=DENSE_VECTOR,  limit=limit),  # by meaning
        models.Prefetch(query=sparse_query, using=SPARSE_VECTOR, limit=limit),  # by keywords
    ],
    "query": models.FusionQuery(fusion=models.Fusion.RRF),   # merge the two ranked lists
}
response = self._client.query_points(self.collection, limit=limit, with_payload=True, **kwargs)
Why RRF (Reciprocal Rank Fusion)? The two searches score on different scales: cosine scores sit around 0–1, BM25 scores can be 0–30. They can't simply be added. RRF ignores the scores and uses positions instead. Each chunk gets 1/(k + rank) from each list, and the scores are added. A chunk that ranks well in both lists comes out on top.

What else lives in PostgreSQL

Qdrant holds the searchable chunks; Postgres holds everything else:

  • Document registry: one row per file (name, hash, chunk count), used to skip unchanged files. Tables are in app/db/schema.sql, code in app/db/repositories.py.
  • Ingest jobs (app/db/jobs.py) and conversations (app/db/sessions.py).
  • Agent memory: LangGraph checkpoints saved after every step, so a conversation survives a restart (app/memory/checkpointer.py:26).

# app/retrieval/retriever.py:65 (shortened)
dense, sparse = self._embedder.embed_query(question)                    # 1. question → vectors
hits   = self._store.search(dense, sparse, mode="hybrid", limit=10)    # 2. Qdrant hybrid + RRF

Why two stages (bi-encoder, then cross-encoder)? The embedding model encodes the question and each chunk separately. That's fast, because the chunk vectors are computed once at ingestion, but it's approximate. The cross-encoder reads the question and a chunk together, which is much more accurate but too slow to run on thousands of chunks. So the fast search picks 10 and the precise model orders them.

Structured output: the judge answers in a fixed format

# app/agent/judge.py:87 — one helper used by every judge call
def _ask(self, schema, system, user):
    try:
        structured = self._model.with_structured_output(schema, strict=True)   # JSON matching a Pydantic class
        result = structured.invoke([SystemMessage(system), HumanMessage(user)])
    except Exception as exc:                  # network, rate limit, bad output…
        log.warning("judge_failed", …)
        return None                           # → the caller uses a safe fallback
    return result if isinstance(result, schema) else None
Why structured output and fallbacks? The agent's next step depends on the judge's answer. Free text like "Yes, I think passages 1 and 3…" is hard to parse reliably. With strict=True, OpenAI must return JSON matching the schema in app/agent/state.py:51–64. If a call still fails, the agent never crashes: grading keeps all chunks, routing falls back to "search", and grounding shows "Not verified".
